BOA Architecture & Mathematical Guide

Welcome to the comprehensive architecture and mathematical guide for the BOA Constrictor repository. This document is designed to take you from a beginner's understanding to an advanced grasp of the core concepts driving this loss-less byte-level compression system.

1. Understanding MAMBA and the Math Behind It

1.1 What is Mamba?

Traditional sequence models, like Transformers, suffer from $O(N^2)$ computational complexity with respect to sequence length due to self-attention. Recurrent Neural Networks (RNNs) scale linearly $O(N)$ but struggle to remember long-term dependencies due to the vanishing gradient problem.

Mamba is a State Space Model (SSM) that achieves the best of both worlds. It maintains a linear $O(N)$ scaling while selectively forgetting or remembering information based on the input itself, allowing it to capture very long-range dependencies efficiently.

1.2 The Continuous State Space Model

At its core, a continuous State Space Model is defined by two linear ordinary differential equations (ODEs):

$$ h'(t) = A h(t) + B x(t) $$ $$ y(t) = C h(t) + D x(t) $$

Where:

  • $x(t)$: Input at time $t$
  • $h(t)$: Hidden state at time $t$
  • $y(t)$: Output at time $t$
  • $A, B, C, D$: Learnable parameter matrices

1.3 Discretization

Since computers process discrete tokens (like bytes), we must discretize these continuous ODEs. We introduce a step size $\Delta$ (Delta). Using the Zero-Order Hold (ZOH) method, the continuous matrices are transformed into discrete ones:

$$ \bar{A} = \exp(\Delta A) $$ $$ \bar{B} = (\Delta A)^{-1} (\exp(\Delta A) - I) \cdot \Delta B $$

The discrete recurrence becomes: $$ h_t = \bar{A} h_{t-1} + \bar{B} x_t $$ $$ y_t = C h_t + D x_t $$

1.4 The Selectivity Mechanism (The "Mamba" Magic)

In standard SSMs (like S4), the matrices $A, B, C,$ and $\Delta$ are static across time. Mamba introduces Selectivity by making $B, C,$ and $\Delta$ input-dependent functions:

$$ \Delta_t = \text{Softplus}(\text{Linear}(x_t)) $$ $$ B_t = \text{Linear}(x_t) $$ $$ C_t = \text{Linear}(x_t) $$

Because the recurrence parameters change at every step based on the input byte $x_t$, the model can "selectively" choose to reset its memory (if a new file block starts) or maintain it (if it's in the middle of a continuous text stream).

2. Understanding the Range Codec and Its Math

2.1 Entropy Coding Basics

Compression relies on Shannon's Entropy. If the model predicts that the next byte is 'E' with 90% probability, we should use very few bits to store 'E'. If it predicts 'Z' with 0.1% probability, we must use more bits if 'Z' actually occurs.

2.2 How Range Coding Works

Range Coding is an integer-based arithmetic coder. Instead of assigning a specific bit-code to each symbol (like Huffman coding), it represents the entire sequence of bytes as a single extremely precise fraction inside the interval $[0, 1)$.

  1. Start with an interval Low = 0 and Range = 1.
  2. For each byte, the neural network predicts a probability distribution.
  3. Convert probabilities to a Cumulative Distribution Function (CDF).
  4. Subdivide the current Range proportionally based on the CDF.
  5. Update Low and Range to match the specific interval of the actual observed byte.
  6. When Range becomes too small, renormalize by shifting out the leading identical bits of Low and High, appending them to the compressed file.

2.3 The Math Behind the Codec

Assume we have $K$ possible byte values (0 to 255). Let the neural network output probabilities $p_i$. In our integer implementation, we scale these probabilities by a massive constant $T$ (total frequency count, e.g., $2^{16}$):

$$ C[k] = \sum_{i=0}^{k-1} \lfloor p_i \times T \rfloor $$

The interval update when symbol $s$ occurs is: $$ \text{Range}_{\text{new}} = \lfloor \frac{\text{Range}_{\text{old}}}{T} \rfloor \times (C[s+1] - C[s]) $$ $$ \text{Low}_{\text{new}} = \text{Low}_{\text{old}} + \lfloor \frac{\text{Range}_{\text{old}}}{T} \rfloor \times C[s] $$

This completely avoids floating-point inaccuracies, ensuring the C++ decoder matches the Python encoder identically.

3. Understanding the BOA Repo

The BOA repository is divided into two distinct but deeply connected environments:

  1. Python / PyTorch Environment (model.py, main.py)
    • Purpose: Fast prototyping, training the neural predictor, and evaluation.
    • Flow: Reads raw bytes -> Embeds them -> Passes through the Mamba/Transformer blocks -> Outputs logits (probabilities).
  2. C++ / CUDA Environment (portability_solved_cpp/)
    • Purpose: Extremely fast, parallelized GPU inference and deterministic Range Coding.
    • Flow: Python saves the model weights. C++ loads them, launches highly optimized CUDA kernels to compute logits across thousands of chunks simultaneously, and runs the Range Coder directly on the GPU.

4. Implementation Walkthrough (Beginner to Advanced)

4.1 Python PyTorch Implementation (Beginner)

Open model.py. You'll see the standard PyTorch structure:

  • Embedding: Converts the byte 0-255 into a dense vector (e.g., size 256).
  • TransformerBlock / LSTMBlock: The sequence modeling layers. They take the dense vectors and contextualize them based on past bytes.
  • Linear Head: Converts the contextualized vector back into 256 logits, representing the probability of the next byte.

When running main.py, the train() loop feeds gigabytes of data through this network, using Cross-Entropy Loss to force the model to predict the next byte accurately.

4.2 Interfacing with the Range Coder (Intermediate)

Once the model is trained, it's useless for compression unless attached to a Range Coder. Look at gpu_range_coder.py. This script bridges Python and C++. Instead of predicting one byte at a time sequentially (which is incredibly slow), we split the file into thousands of chunks. The gpu.queue.RangeCoderBatch takes the logits produced by PyTorch and passes them to the C++ backend to be squashed into a bitstream in parallel.

4.3 C++ CUDA Implementation (Advanced)

Open boa_gpu.hpp and gemm_gpu.hpp in the portability_solved_cpp folder.

This is where the true engineering lies. PyTorch is too heavy and non-deterministic for a portable decompressor.

  • BoaBlockGPU: A custom implementation of the sequence layers (like Mamba or GRU) written in pure C++ and raw CUDA kernels.
  • gemm_gpu_batch: Instead of relying heavily on external bloated libraries, we use strided batched GEMMs (General Matrix Multiplications) to process all chunks simultaneously.
  • gpu_rc_encode_step_batch: The CUDA kernel that implements the integer Range Coding math described in section 2.3. Every CUDA thread handles one chunk, updating its RCState (lower and range) and writing out compressed bits entirely on the GPU.

By keeping everything on the GPU and avoiding GPU-to-CPU copies for every byte, BOA achieves massive compression throughput, solving the notorious bottleneck of Neural Data Compression.
